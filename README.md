## Overview

**Ustam** is a full-stack, mobile-first web application — a marketplace for daily, short-term and one-off jobs. Workers (tradespeople, cleaners, loaders, drivers, etc.) offer their services or apply to job posts, while employers publish jobs and hire nearby talent.

The app is built with a modern React SPA frontend and a **Supabase** (PostgreSQL) backend that provides authentication, database, row-level security, file storage and **realtime** messaging. It is fully responsive, supports **dark mode** and ships in **three languages** (Uzbek, Russian, English).

The project was built as a portfolio piece demonstrating:

- Clean, feature-based frontend architecture
- Server-state management with **RTK Query**
- Secure, role-based access control enforced in the database with **RLS policies**
- Realtime features (chat) and database-trigger-driven notifications
- A production-style Supabase schema with migrations

## Key Features

### Authentication & Profiles

- Email/password authentication with **Supabase Auth**
- Role-based registration (**Worker** / **Employer**)
- Forgot-password and reset-password flow (email link)
- Guided **onboarding** — fill in profile and pick profession categories
- **Profile photo upload** to Supabase Storage (`avatars` bucket) with client-side validation
- Editable profile: name, phone, city, district, bio, hourly rate, **profession categories**
- Public worker profile with rating, completed-jobs count and reviews

### Jobs (Employers)

- Create / edit / delete job posts (category, city/district, price, price type, workers needed, date)
- Mark a job as `open` / `in_progress` / `completed` / `cancelled`
- Browse, search, filter (category, city) and sort jobs
- Review applications and **accept / reject** candidates
- Leave a rating & review after completion

### Workers

- Browse and apply to jobs (application message + proposed price)
- Track sent applications and their status
- Publish **service ads** (`worker_ads`) offering their own skills — toggle active/inactive
- Personal **dashboard** with statistics and charts (applications, completed jobs, earnings, activity)

### Real-time Chat

- 1:1 messaging between users powered by **Supabase Realtime**
- Unread-message badges, auto-scroll, mark-as-read

### Notifications

- In-app notifications generated by **database triggers** (new application, accepted/rejected)
- Unread badge in the header and bottom navigation, "mark all as read"

### UX / Interface

- Mobile-first layout with a bottom navigation bar and a desktop header
- **Dark mode** with system preference detection and persistence
- Animations via **Framer Motion**
- Toast notifications and error boundaries
- Skeleton loaders and empty states

## How It Works

Ustam has two primary roles — **workers** and **employers** — sharing one realtime layer.

**Worker journey**

1. Sign up as a **Worker** and pick profession categories during onboarding.
2. Browse jobs (filter by category and city) or publish a **service ad**.
3. Apply to a job with a short message and a proposed price.
4. Get an in-app notification when accepted, then agree on details over **realtime chat**.
5. Complete the job and receive a **rating & review**.

**Employer journey**

1. Sign up as an **Employer** and complete the company profile.
2. Post a job — category, city/district, price and price type, number of workers and date.
3. Review incoming applications and **accept** or **reject** candidates.
4. Chat with the accepted worker and close the job as **completed**.
5. Leave a **rating & review** for the worker.

**Behind the scenes**

- Applications and status changes fire **database triggers** that create notifications.
- Chat messages stream in over **Supabase Realtime** and are cached by RTK Query.
- Average rating and completed-job counts are computed by **RPC functions**.

## Architecture

The app is a client-side SPA that talks **directly** to Supabase (no custom backend). Security is enforced at the database layer through **RLS policies**, so the same anon key is safe to ship to the browser.

```
┌────────────────────────────┐        ┌──────────────────────────────────┐
│         Browser            │        │            Supabase              │
│                            │        │                                  │
│  React + Vite (SPA)        │  HTTPS │  PostgREST (auto REST API)       │
│   ├─ Redux Toolkit store   │ ─────► │   ├─ PostgreSQL + RLS policies   │
│   ├─ RTK Query (data layer)│        │   ├─ GoTrue  (Auth)              │
│   ├─ React Router          │        │   ├─ Storage (avatars, images)   │
│   └─ i18next (uz/ru/en)    │  WS    │   ├─ Realtime (chat)             │
│                            │ ◄────► │   └─ Triggers / RPC functions    │
└────────────────────────────┘        └──────────────────────────────────┘
```

**Data flow**

1. UI components dispatch RTK Query hooks (e.g. `useGetJobsQuery`).
2. RTK Query calls Supabase through typed API modules in `src/features/*`.
3. Supabase RLS validates the JWT and returns only permitted rows.
4. RTK Query caches the result and invalidates tags on mutations.
5. Realtime subscriptions (chat) push updates and trigger cache invalidation.

**Design principles**

- **Feature-based** folders: each feature owns its RTK Query API and slice.
- **UI primitives** separated from **domain components**.
- **Central data layer** via RTK Query — components stay declarative.
- **Validation** shared through Zod schemas in `src/utils/validators.js`.

## Database

The dataset lives in **PostgreSQL** on Supabase. Key tables:

| Table               | Purpose                                                    |
| ------------------- | ---------------------------------------------------------- |
| `profiles`          | User profile, linked to `auth.users` (role, bio, avatar…)  |
| `categories`        | Profession categories (Builder, Plumber, Electrician…)     |
| `worker_categories` | Many-to-many: worker ↔ categories (specialties)            |
| `jobs`              | Employer job listings                                      |
| `worker_ads`        | Worker service ads (offer own skills)                      |
| `applications`      | Worker applications to jobs + status                       |
| `reviews`           | Ratings and reviews after job completion                   |
| `notifications`     | In-app notifications                                       |
| `messages`          | 1:1 chat messages (Realtime enabled)                       |

**Security & automation**

- **RLS** is enabled on every table — e.g. profiles are public-read/owner-write, messages are visible only to participants, notifications only to their owner.
- **Triggers** create a profile on sign-up, and generate notifications on new applications / status changes (via `SECURITY DEFINER` functions).
- **RPC functions**: `get_worker_rating`, `get_worker_completed_jobs`.
- **Storage buckets**: `avatars`, `job-images` (public read, authenticated write).

See [`supabase/schema.sql`](supabase/schema.sql) for the full definition.

## Getting Started

### Prerequisites

- Node.js **18+**
- A **Supabase** project ([supabase.com](https://supabase.com))

### 1. Clone & install

```bash
git clone https://github.com/gayratov993/ustam.git
cd ustam
npm install
```

### 2. Create the database

In your Supabase project → **SQL Editor**, run the contents of:

1. `supabase/schema.sql` — tables, RLS, triggers, functions, buckets, seed categories.

If you already have a database from an earlier version, run the migration instead:

2. `supabase/migration_notifications_and_role.sql` — applies the latest changes idempotently.

### 3. Configure environment

Copy `.env.example` to `.env.local` and fill in your project keys:

```bash
cp .env.example .env.local
```

```env
VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR-ANON-PUBLIC-KEY
```

### 4. Run

```bash
npm run dev
```

Open `http://localhost:5173`.

## Security

- Access control is enforced **in the database** with PostgreSQL **Row Level Security** on every table — the client can never bypass it.
- Only the **anon (public) key** is shipped to the browser. The **service-role key is never used** in the frontend.
- Profiles are public-read / owner-write; chat messages are visible only to their participants; notifications only to their owner.
- Notifications and profile creation run inside `SECURITY DEFINER` trigger functions to avoid privilege escalation.
- Storage buckets are **public-read** but **authenticated-write**, with file-type and size validation on the client.

## Deployment

The app is a static SPA and deploys to any static host (Vercel, Netlify, Cloudflare Pages).

**Vercel**

1. Import the repository on [vercel.com](https://vercel.com).
2. Framework preset: **Vite** (build command `npm run build`, output directory `dist`).
3. Add environment variables `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`.
4. Add your Vercel domain under Supabase → **Authentication → URL Configuration → Redirect URLs**.
5. Deploy.

Because it uses client-side routing, add an SPA rewrite so every route falls back to `index.html`.
